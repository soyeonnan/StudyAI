# 설계 트레이드오프

주요 설계 결정에서 무엇을 얻고 무엇을 포기했는지 정리했습니다.

## 1. 루틴: effective date 버전 관리 vs 스냅샷

- **선택**: effective date 버전 관리(버전마다 유효기간).
- **얻은 것**: 완전한 변경 이력, 과거·현재·미래 독립, "언제 무엇이 유효했는가"를 정확히 재현.
- **포기한 것**: 구현 복잡도 증가. 특정 날짜 조회 시 유효 버전을 찾는 쿼리가 필요.
- **대안(스냅샷)**: 날짜별로 루틴 목록을 통째 복사. 단순하지만 데이터 중복이 크고
  루틴 하나만 바꿔도 관리가 번거로움.
- **결론**: "과거 불변 + 이력 추적"이 핵심 요구라 버전 관리가 적합.

## 2. 대시보드 집계: 백엔드 API vs 프론트 계산

- **선택**: 백엔드에 집계 엔드포인트(`/stats/daily`, `/stats/monthly`).
- **얻은 것**: 정확도(단일 소스에서 계산), 네트워크 전송량 감소, 재사용성.
- **포기한 것**: 백엔드 엔드포인트가 늘어남.
- **대안(프론트 계산)**: 원자료를 모두 받아 브라우저에서 계산. 서버는 단순하지만
  데이터가 많아지면 비효율적이고 계산 로직이 프론트에 흩어짐.

## 3. 비밀번호 해싱: bcrypt 직접 사용 vs passlib

- **선택**: `bcrypt` 라이브러리 직접 사용.
- **이유**: passlib 1.7.x가 최신 bcrypt(4.x/5.x)와 호환 문제가 있어(내부 버전 조회 실패)
  런타임 오류가 발생. passlib은 유지보수가 정체된 상태.
- **포기한 것**: passlib이 제공하는 다중 해시 스킴 추상화. (이 앱은 bcrypt 하나면 충분)
- **주의**: bcrypt는 72바이트 초과 입력을 자르므로, 입력을 명시적으로 72바이트로 잘라 일관 처리.

## 4. 차트: 직접 구현(SVG/CSS) vs 라이브러리

- **선택**: 직접 구현.
- **얻은 것**: 의존성/번들 절감, 완전한 커스터마이징, 학습 효과.
- **포기한 것**: 복잡한 차트(툴팁·확대 등)를 빠르게 붙이는 편의.
- **결론**: 요구가 막대/도넛 수준이라 직접 구현이 합리적.

## 5. 모니터링: 항상 실행 vs 선택 실행

- **선택**: 별도 compose 파일로 **선택 실행**.
- **얻은 것**: 평소 리소스 절약, 앱과 모니터링의 관심사 분리.
- **포기한 것**: 항상 켜두는 편리함(대신 `-f`로 함께 실행하면 됨).

## 6. DB 스키마 변경: drop & recreate vs 마이그레이션(Alembic)

- **현재 선택**: 개발 단계라 `DROP SCHEMA` 후 재생성.
- **얻은 것**: 빠른 반복 개발.
- **포기한 것**: 데이터 보존. 운영 전환 시에는 **Alembic 도입이 필요**(향후 과제).

## 7. 인증 상태: JWT(무상태) vs 서버 세션

- **선택**: JWT(localStorage 저장, 요청마다 헤더 첨부).
- **얻은 것**: 서버 무상태 → 수평 확장 용이.
- **포기한 것/주의**: 토큰 탈취 대비(XSS 예방), 만료·갱신 전략 필요. 현재는 만료 시간으로 관리.

## 향후 개선 과제

- Alembic 마이그레이션 도입
- 리프레시 토큰 및 토큰 회전
- 통합/단위 테스트 스위트 추가
- 루틴 요일 지정 UI 고도화
