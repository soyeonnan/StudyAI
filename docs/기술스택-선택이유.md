# 기술 스택 선택 이유

각 기술을 왜 선택했는지, 대안과 비교해 정리했습니다.

## 백엔드: FastAPI

- **타입 기반 자동 검증/문서화**: Pydantic으로 요청을 검증하고, `/docs`(Swagger)가 자동 생성됩니다.
- **비동기 지원**과 준수한 성능.
- **학습 곡선이 완만**하고 코드가 간결합니다.
- 대안: Flask(문서화/검증을 직접 붙여야 함), Django(풀스택이지만 이 규모엔 무거움).

## ORM: SQLAlchemy 2.0

- **DB 독립성**: 같은 코드로 SQLite ↔ PostgreSQL 전환(`DATABASE_URL`만 변경).
- **명시적 매핑**(`Mapped`, `mapped_column`)으로 타입 안전성.
- 원시 SQL 대신 파라미터화 쿼리를 자동 사용 → **SQL 인젝션 예방**.

## 데이터베이스: PostgreSQL (개발 SQLite)

- 데이터가 관계형(사용자–과목–기록, 루틴–버전–완료)이라 조인·집계에 유리.
- 통계/분석 확장(윈도우 함수 등)에 강함.
- 개발 초기에는 SQLite로 마찰 없이 시작하고, 운영은 PostgreSQL.

## 인증: python-jose(JWT) + bcrypt

- **JWT**: 서버가 세션을 저장하지 않는 stateless 인증. 확장에 유리.
- **bcrypt**: 검증된 비밀번호 해싱. (passlib 대신 bcrypt를 직접 사용 — 최신 bcrypt와 passlib의
  호환성 문제를 피하기 위함. [트레이드오프 문서](트레이드오프.md) 참고.)

## 프론트엔드: React + Vite

- **컴포넌트 재사용**과 상태 관리가 이 앱(타이머·캘린더·대시보드)에 잘 맞음.
- **Vite**: 빠른 개발 서버와 빌드.
- 라우팅은 **React Router**, HTTP는 **Axios**(인터셉터로 JWT 자동 첨부/401 처리).

## 그래프: 외부 차트 라이브러리 없이 SVG/CSS

- 일별 공부량 막대·진행률 링을 직접 구현.
- 이유: 번들 크기 절약, 의존성 최소화, 커스터마이징 자유. 학습 목적에도 부합.
- 대안: Recharts/Chart.js(빠르지만 의존성·번들 증가). 요구 수준이 단순해 직접 구현이 합리적.

## 인프라: Docker + docker-compose + Nginx

- **재현성**: `docker compose up` 한 번으로 db+backend+frontend 기동.
- **Nginx**: 프론트 정적 파일 서빙 + `/api` 프록시.
- 모니터링 스택은 **별도 compose 파일**로 분리해, 평소엔 앱만 띄워 리소스를 아낌.

## 모니터링: Prometheus + Grafana + Loki + Promtail

- **Prometheus**: 메트릭 수집(요청 수/지연/상태코드). 백엔드가 `/metrics`로 노출.
- **Loki + Promtail**: 컨테이너 로그 수집·조회.
- **Grafana**: 메트릭·로그 시각화. 데이터소스와 대시보드를 자동 프로비저닝.
- 관측성(observability)은 실무에서 중요한 역량이라 포함.
